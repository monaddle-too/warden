# Cloud organizations

Status: deployed 2026-09-26 from `feat/cloud-organizations` (based on `origin/main` 50b809b); branch remains unmerged. Cloud service state is in PostgreSQL and legacy service volumes are detached.

## Objective

Make the cloud deployment a multi-organization service. The full admin can create organizations and assign administrators. Administrators manage named users by email, and every administrator can use the normal workspace features. Users sign in with an emailed one-time code and may register a passkey for later verification. Organization data, including Panta Docs and drawings, is visible to its members only. Cloud application data belongs in a database instead of local service volumes. Until account-specific provider credentials exist, cloud agents use the full admin's Codex and Claude credentials.

## What exists

The GKE deployment uses four Warden services (`edge`, `chat`, `policy`, `runner`) and Google or owner-capability sign-in. Edge sessions are in a JSON file; chats and runner state use private SQLite files; policy and attachments also use files on mounted volumes. `docs/feature-map.md` maps the routes and components. The separate `project-management-software` checkout contains Panta Docs and design tooling in `apps/docs`, including the drawing/design app. Current cloud login has no organization principal, and Warden's owner role is global. The Panta production hostname is not part of this deployment.

## Steps

1. Inventory persistent cloud state, identity propagation, Panta Docs and drawing ownership, and the live deployment; choose a database and migration path that preserves existing data.
2. Add organization, membership, human name, full-admin and org-admin models with guarded admin APIs and UI.
3. Replace cloud Google sign-in with emailed codes sent through SMTP and optional passkeys; migrate sessions to the database.
4. Enforce organization scope on every workspace, chat, preview, document, image, and admin route, including agent paths.
5. Put cloud application state in the database, integrate Panta Docs and drawings with organization scope, and reuse the full admin's Codex/Claude credentials without exposing them to users.
6. Run focused and full tests, exercise an upgrade and rollback against a staging database, deploy to the requested cloud environment, and verify live sign-in and cross-organization isolation.

## Key decisions

1. Keep local owner-mode behavior intact; this work targets the cloud deployment.
2. Treat server-side authorization as the boundary; UI filtering only improves usability.
3. Owner explicitly confirmed on 2026-09-26 that all internal durable state must move to PostgreSQL before cutover. Retaining internal policy files is not an accepted transitional exception. The SMTP setup is complete; it does not remove this release gate.

## Remaining database-only release gate

- Policy sharing and provider connection tables: `sharing.sqlite`, `google.sqlite`, including image bytes, document proposals, pull request proposals, repository selections and history.
- Per-sandbox control tables: requests, grants and decisions in `control.sqlite`; preserve restart revocation and stale-request behavior.
- Policy documents, egress settings and overrides, active/retired binding generations, gateway port records and network-disconnect markers.
- Gateway certificate authority: import the existing private key and certificate without rotating it; retain transactional rotation and fail closed on database errors.
- Hash-chained audit events: append individual durable rows before permitting operations; preserve historical events and ordering.
- Kubernetes identity pins in `kube-runtime-identities.json`: persist before accepting the identity, preserving storage-failure behavior.
- Replace service-volume locks with database ownership locks where required; keep sockets and transient workspace execution artifacts separate from durable service state.
- Verify migration idempotency and crash recovery against an isolated copy, then restart against PostgreSQL with legacy service volumes read-only to catch remaining writes. Rebuild images only after these gates pass.
