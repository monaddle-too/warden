Connect your recorder

Register a device in Recordings → Manage devices, copy its key once, and send audio. Recordings and transcripts are visible to everyone in your organization.

Download Python client · OpenAPI HTTP spec · AsyncAPI WebSocket spec

Quick start

Python 3.10+ and a mono, 16 kHz, 16-bit PCM WAV file. Substitute your Warden origin for SERVER below. The client asks for the device key in a hidden prompt; do not put secrets in commands or URLs.

python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install websockets==15.0.1
python3 warden_record.py upload recording.wav --server https://SERVER --title "First upload"
python3 warden_record.py stream recording.wav --server https://SERVER --title "Live test" --reconnect-after 5

Upload sends the WAV samples through resumable HTTP chunks. Stream sends 100 ms audio chunks over a secure WebSocket at real-time speed, deliberately disconnects once, and resumes. Both print the recording link. Use --recording-id ID with the same original WAV to resume after stopping the script. Reuse the printed --operation-id if recording creation was interrupted. WARDEN_DEVICE_KEY can supply the key from your development environment.

Device protocol

  1. POST /v1/recordings with metadata below, authenticated with Authorization: Bearer DEVICE_KEY.
  2. Open wss://SERVER/v1/recordings/ID/stream with the same header. Do not send an Origin header.
  3. Read the initial status message. Resume using its recording.nextSeq and recording.bytes.
  4. Send binary messages: 8-byte unsigned sequence number in big endian, followed by signed 16-bit PCM samples in little endian. Use mono 16 kHz. Recommended payload: 3,200 bytes / 100 ms; maximum: 32,000 bytes / one second.
  5. Wait for {"type":"ack","nextSeq":N} before discarding local audio. The acknowledgement means the audio is committed to PostgreSQL. Keep unacknowledged data across reconnects. One active writer per recording.
  6. Finish with {"type":"finish","nextSeq":N}, or POST the final count to /v1/recordings/ID/finish. A lost finish response is safe to retry.
{
  "operationId": "a-unique-uuid-for-this-recording",
  "title": "Desk recorder",
  "mode": "stream",
  "encoding": "pcm_s16le",
  "sampleRate": 16000,
  "channels": 1,
  "language": "en-US"
}

Status messages every three seconds contain recording and transcription states, finalized segments, and provisional text. Provisional text may change. Reconnect and fetch status to recover the full snapshot; there is no need to replay transcript events.

HTTP uploads and recovery

Create with mode: upload, then either PUT a PCM WAV to /v1/recordings/ID/upload (maximum 32 MiB), or PUT raw PCM to /v1/recordings/ID/chunks/SEQUENCE and POST /finish. Whole-file retries must use identical data and chunk boundaries. Repeated chunks are accepted only if their digest matches. A 409 means a sequence, metadata, or lifecycle conflict; fetch status before proceeding.

On 429, keep audio and wait at least five seconds. On 502/503/504 or connection loss, retry with exponential backoff, fetch status, and resume. On 401/403, stop and replace the key or check membership. Never generate new recording IDs just to retry chunks. The device must retain unsent audio if its network is unavailable; the server cannot recover audio it never received.

States and limits

Recordinglive, uploading, interrupted (no data for 15 seconds), finished
Transcriptionwaiting, transcribing, complete, failed
Limits2 hours/recording; 2 unfinished recordings/device; 20 active devices/member; 100 new recordings/day/organization; roughly 5 MiB unprocessed audio before backpressure

Transcription uses Google Speech-to-Text in short windows: a provisional pass around five seconds and finalized segments around ten seconds or at finish. English (US) initially. Short-window boundaries can lose context; accuracy, speaker identification, and summaries are future work. Silent segments may legitimately have no text.

Finished audio becomes playable when archived. Private object storage holds finalized audio; PostgreSQL holds metadata, transcripts, and the durable ingest queue. Processing restarts recover automatically. Failed transcription can be retried from the web UI without uploading again.

Credentials and access

Device keys are shown once and stored as hashes. A key can submit and inspect only its own device's recordings. It cannot list organization recordings or read documents. Its owner or an organization administrator can replace or revoke it; removing its owner from the organization disables access. Browser management uses the normal session and CSRF protection. Recording metadata and audio stay scoped to the organization.

The API version is v1. HTTP endpoints are described in OpenAPI and WebSocket messages in AsyncAPI. Browser live updates use authenticated server-sent events under /api/recordings/events.
